# AI 补全体验评估

2026-09-29；依据当前源码与已安装 Fastab 的真实 `specs-ir`，未调用外部 AI API。

## 结论

当前 AI 是“从已有候选中选一项置顶”，体感有限主要受候选覆盖、上下文和响应时机限制。先改善候选供给与交互稳定性，再评估模型收益；不能把黄色星标出现次数当作补全质量。

## 已核实的限制

1. **候选预算在本地排序前用完。** `lookup.rs` 先按名字排列静态子命令，在采集时分配最多 20 个 AI 标记，之后才由 `rank.rs` 排序。即使本地历史把某个后面的命令排到首位，该项也可能没有 AI 资格。
2. **常用参数场景没有覆盖。** `public_ai.rs` 只接受可追溯的公开静态命令/选项和受限字面输入。路径、引号、管道、已消费选项、动态 generator、实际生效的 alias 展开，以及分支名等参数值会被排除。这个边界有数据来源与插入安全方面的作用，不应直接去掉过滤。
3. **已有上下文仍不足以判断任务。** 当前已发送本次输入、Git 分支和同目录最近最多 10 条命令（2 KiB 总上限）。但分支名不能说明有没有改动、有没有暂存、是否落后远端；最近命令也不能说明执行是否成功。不能把“加历史记录”当作尚未实现的新能力。
4. **很容易来不及使用。** 最终本地结果后等待 250 ms，收集上下文最多等待约 200 ms，HTTP 有 2 s 超时；这些是代码预算，不是实测延迟。继续输入、开始方向键选择都会使在途结果失效。每分钟最多 20 次，当前没有推荐结果缓存。
5. **收益不可量化。** 响应中的概率和 confidence 经格式校验后被丢弃，未形成经过评估的置信度策略；暂时失败在列表中静默退回本地，缺少覆盖率、耗时、取消原因、置顶后采用/跳过的本地汇总。静默回退可保持界面安静，但设置页应能解释“为什么没有参与”。

## 本地引擎样例

使用当前源码编译的引擎、已安装应用的受信任 spec 数据；空 cwd 禁止动态脚本，空历史输入，不发网络请求。数量只描述这组确定性样例，不能当作用户整体覆盖率或准确率。

| 输入 | 本地项数 | AI 可用项数 | 观察 |
| --- | ---: | ---: | --- |
| `git ` | 61 | 20 | 仅 `add` 到 `init`；不含 `status`、`switch`、`pull`、`push` |
| `git ch` | 2 | 2 | 仅在 `checkout` / `cherry-pick` 中选择 |
| `git --` | 14 | 14 | 静态选项可参与 |
| `git status --` | 17 | 17 | 静态选项可参与 |
| `git checkout ` | 68 | 0 | 参数场景被排除 |
| `git -C /tmp ch` | 2 | 0 | 已消费选项/路径不符合当前边界 |
| `npm run ` | 7 | 0 | 当前参数场景不参与；空 cwd 未执行项目脚本生成器 |
| `docker ` | 60 | 20 | 同样只有靠前的静态子命令 |
| `kubectl get ` | 21 | 0 | 资源参数场景不参与 |
| `echo hello \| git ch` | 2 | 0 | 复合命令不参与 |

另一个验证注意点：本机工作区生成的 `bundle/specs-ir` 与当前 AI 固定基线不一致，而 `/Applications/Fastab.app/Contents/Resources/specs-ir` 的三个基线摘要均匹配。因此上述样例使用安装包数据。后续打包应检查基线；不能为了让 AI 工作而直接信任任意生成目录或修改摘要。

## 建议实施顺序

### 1. 先让现有推荐真正看见有用候选

- 在来源校验时保留资格，在本地排序完成后才截取最多 20 项，确保当前首项在候选集合内；保持来源校验、去重和插入元数据的完整性。
- 优先处理多候选、含义有歧义的场景；准确前缀已唯一确定时直接使用本地结果。
- 已开始选择后保持行顺序；不抢选中项，不把接受动作变成执行命令。
- 设置页增加仅本机汇总的“参与/跳过原因、延迟、失败状态”。普通列表保持安静，计数不保存原始命令或密钥。

### 2. 增加可解释的任务上下文和缓存

- Git 场景先试用本地提取的结构化信号，如是否有改动/暂存/冲突，而不是上传文件内容；新增外发范围需让用户选择。若已确认的本地状态足以决定排序，优先使用本地规则。
- 短时缓存以命令路径、输入、候选身份、项目上下文版本、模型/配置为键；会话、目录、Git 状态或配置改变时失效。只缓存候选身份，不缓存可执行字符串，也不跨项目复用。
- 概率只能作为待校准的排序信号。通过样例确定何时保持本地顺序，不能随意把某个 confidence 阈值称作准确率保证。

### 3. 扩展最有体感的参数选择

- 优先评估 `git checkout <branch>`、`npm run <script>`、`docker <container>` 等真实高频候选的本地排序。分支、脚本、容器名可能包含私人信息，远端推荐必须单独定义数据范围，不能冒充“公开静态候选”。
- 现有接受记录按根命令+候选名保存，已有历史频次排序；可以进一步按项目/子命令上下文区分，避免项目 A 的常用参数干扰项目 B。
- 自然语言生成整条命令、根据错误输出给出修复建议，应作为用户主动触发的独立模式设计。当前 Jev 客户端契约只返回已有候选 ID，这不是修改现有推荐提示词就能实现的功能。输出先预览、确认插入，仍由用户执行。

## 评估与复核标准

先建立有明确意图的固定场景集，比较“现有本地排序 / 改善后的本地排序 / AI 推荐”，记录命中位置、到目标项的按键数、有效覆盖率、可见延迟和额外请求数。再在用户同意的真实使用中收集本机汇总，区分 AI 已返回、确实改变排序、用户采用三个事件。暂不宣称任何方案已经提高准确率。

优先级：候选截取与可诊断性 → 项目上下文与缓存 → 动态参数 → 独立自然语言模式。本轮只交付探索结论，前三个交互问题另行修复。
